⚠ Vexis automatically adjusts certain Windows security settings on startup to enable hardware sensor access. Use this page to control exactly what gets changed — and understand why each setting exists before deciding to turn it off.

Changes take effect on next restart of Vexis. Some require a Windows reboot.
STARTUP SECURITY SETUP
When enabled, Vexis checks and applies your selected security settings every time it starts. Disable this if you want to manage Windows security settings manually.
🛡 MEMORY INTEGRITY (HVCI) AUTO OFF
📖
What it does
Memory Integrity (formally Hypervisor-Protected Code Integrity / HVCI) uses hardware virtualization to run the Windows kernel code integrity checks inside a protected environment. It prevents unsigned or vulnerable kernel-mode drivers from loading, even if an attacker has modified them.
🔒
Why Microsoft built it
Protects against rootkits, bootkits, and sophisticated malware that installs itself as a kernel driver. It's one of the core Windows 11 security requirements because modern attacks frequently exploit the kernel rather than user-mode software.
⚙
Why Vexis needs it off
WinRing0x64.sys — the driver that reads per-core CPU temperatures and clock speeds — is listed on Microsoft's vulnerable driver blocklist. Memory Integrity refuses to load it. Without this driver, Intel per-core temps and clocks are unavailable. AMD systems often work without it.
⚠
What you lose when it's off
A malicious kernel-mode driver could load and gain full system access. This is a realistic threat vector for targeted attacks, less so for everyday users. Game anti-cheat software (Valorant's Vanguard, FACEIT) may refuse to run without Memory Integrity enabled.
🔍
Things to consider
If you only play games with kernel-level anti-cheat, keep Memory Integrity ON and accept limited Intel sensor data. If you're on AMD, WinRing0 may not be required at all — AMD SMU access uses a different path that often works without this driver.
⬤ MEDIUM RISK when off — primarily a concern for targeted attacks or kernel-level anti-cheat games
🚫 VULNERABLE DRIVER BLOCKLIST AUTO OFF
📖
What it does
Microsoft maintains a list of drivers known to have security vulnerabilities. The Vulnerable Driver Blocklist prevents these drivers from loading, even if they have valid signatures. The list is updated via Windows Update and covers thousands of known-bad driver versions.
🔒
Why Microsoft built it
Defends against BYOVD (Bring Your Own Vulnerable Driver) attacks — a technique where attackers drop a legitimate but exploitable driver onto a system to bypass OS protections and escalate privileges. This has been used in real-world ransomware and APT attacks.
⚙
Why Vexis needs it off
WinRing0x64.sys is on the blocklist. The same driver is used by HWiNFO64, CPU-Z, and MSI Afterburner — they all face the same issue. The blocklist doesn't distinguish between a hardware monitoring app and a malicious use of the same driver.
⚠
What you lose when it's off
Known-vulnerable drivers can load. An attacker who can drop a file on your system could use one of these drivers to escalate from user to kernel privileges. This is the same technique used by BlackByte, AvosLocker, and other ransomware strains.
🔍
Things to consider
The practical risk depends on how an attacker gets onto your system in the first place. If you practice good security hygiene (no pirated software, updated Windows, not clicking random links), the residual risk is low. HWiNFO64 is a widely-used alternative that faces the same trade-off.
⬤ HIGHER RISK when off — BYOVD is a documented real-world attack vector used in ransomware
🔐 VIRTUALIZATION-BASED SECURITY (VBS) AUTO OFF
📖
What it does
VBS uses the CPU's hardware virtualization (Intel VT-x / AMD-V) to create an isolated secure environment called the Virtual Secure Mode (VSM). Critical security components — including credential hashes, kernel code, and key material — are stored inside VSM where even a compromised kernel cannot access them.
🔒
Why Microsoft built it
Protects against pass-the-hash attacks, credential theft (mimikatz style), and kernel exploits. With VBS on, even full kernel control doesn't give an attacker access to login credentials. It's a core part of Windows 11's security baseline.
⚙
Why Vexis needs it off
VBS enforces Memory Integrity (HVCI). Disabling VBS is sometimes required when HVCI can't be individually toggled — on some system configurations, VBS and HVCI are linked. Vexis disables this as a fallback if the HVCI key alone is insufficient.
⚠
What you lose when it's off
Credential Guard is disabled — your NTLM hashes and Kerberos tickets are no longer isolated in VSM. A kernel-level exploit can now extract credentials from LSASS memory. This is the technique used in most enterprise network compromises (pass-the-hash, pass-the-ticket).
🔍
Things to consider
For home users and gaming PCs, VBS off is the norm — most games and hardware tools require it. The credential theft risk is primarily relevant in domain-joined enterprise environments. If your PC is on a corporate network, consult your IT team before disabling VBS. Requires a reboot to take effect.
⬤ MEDIUM RISK for home users — HIGH RISK on domain-joined corporate PCs
🛡 WINDOWS DEFENDER EXCLUSION AUTO ON
📖
What it does
Adds Vexis's executable and the hardware sensor driver (LibreHardwareMonitorLib.sys) to Windows Defender's exclusion list. Excluded paths and processes are not scanned for malware in real time.
🔒
Why Microsoft built it
Defender's exclusions exist to reduce false positives for legitimate software that uses techniques that look similar to malware — such as low-level hardware access, process injection, or kernel drivers.
⚙
Why Vexis needs it
LibreHardwareMonitorLib.sys triggers Defender's heuristics because it accesses hardware registers at the kernel level — the same technique used by some rootkits. Without the exclusion, Defender may quarantine the driver and prevent sensor readings from working.
⚠
What you lose when it's on (exclusion applied)
If Vexis's install folder is ever compromised by malware, Defender won't detect it. This is an unlikely scenario if you downloaded Vexis from the official GitHub release, but worth understanding.
🔍
Things to consider
The exclusion is narrowly scoped to Vexis's process and the LHM driver temp file. It doesn't exclude your entire PC or install folder. If you see Defender alerts about Vexis, that's likely a false positive — but you can verify by checking the file hash against the GitHub release.
⬤ LOW RISK — narrowly scoped exclusion; only affects the Vexis process and sensor driver
🌐 OPENRGB FIREWALL RULE (PORT 6742) AUTO ON
📖
What it does
Adds a Windows Firewall inbound rule allowing TCP connections on port 6742 — the port OpenRGB's SDK server listens on. Without this rule, Windows Firewall may block Vexis from connecting to OpenRGB.
🔒
Why Windows Firewall exists
The Windows Firewall blocks unsolicited inbound connections by default, preventing external hosts from reaching services running on your PC. This is a critical network boundary control.
⚙
Why Vexis needs it
Vexis communicates with OpenRGB via its local network API (REST on port 6742). If the Firewall blocks this port, the RGB control page can't connect to OpenRGB even though both are running on the same machine.
⚠
What you lose when it's on (rule applied)
Port 6742 is open to inbound connections. Since OpenRGB binds to 127.0.0.1 (localhost only) by default, external machines on your network cannot reach it. Any process running locally on your PC can connect to OpenRGB and control your RGB devices.
🔍
Things to consider
The localhost-only binding means this is essentially a local IPC channel, not a network exposure. The realistic threat is another local application taking control of your RGB — not an external attacker. If you don't use the RGB control page, you can safely disable this rule.
⬤ LOW RISK — localhost only; no external network exposure when OpenRGB uses its default binding
